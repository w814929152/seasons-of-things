# ADR-001：时刻状态模型选型（只读链 + 玩家覆盖层）

- **状态**：已采纳（对齐 GDD §3、§4）
- **决策者**：engineering-lead
- **关联**：architecture.md §3.2 / §3.3 / §5

## 上下文
解密游戏核心是"同一实体在若干离散时刻各有状态"，且玩家操作会改写时间线。需要一个数据模型存储"实体 × 时刻"状态，并容纳玩家写入。GDD 已拍板：离散时刻、全局单一时刻、玩家可改写过去但只影响未来。

## 候选方案

### 方案 A：per-entity 只读状态链 + 玩家 Override 覆盖层 ✅
- 每个 `TimeEntity` 持有只读 `chain: Array[StateFrame]`（长度 == 时刻数，策划写真值表）。
- 玩家操作写入 `Override`（带 `t_index` / `field` / `value` / `propagate` / `seq` / `parent_seq`）。
- 世界呈现 = `resolve_state(实体, t)`：取 `chain[t]`，叠加所有 `t_index <= t` 的 Override（后写覆盖先写）。

### 方案 B：全局快照（存整关每时刻完整快照）
- 关卡级 `snapshots: {t: WorldSnapshot}`。

### 方案 C：事件溯源（只存操作序列，状态重放推导）
- 只存操作日志，任意时刻状态 = 从初态重放。

## 决策：方案 A（GDD 已定）

**理由：**
1. **契合数据形态**：真值表天然是"每实体按时刻排开的只读链"（KEY 的锭→新→锈→块），策划直接照抄 GDD 表格。
2. **悖论免疫（关键）**：历史是**只读常量**，任何时刻状态都是对常量 + 有限 Override 的确定性求值 → 系统**绝不崩溃**，不存在"算不出来的悖论"。方案 C 若操作日志含非法因果会陷入未定义。
3. **作者友好 + 局部性**：改一个实体的形态链只动该实体数据；Override 局部追加。
4. **对比 B**：全局快照把同一实体各时刻状态打散，作者编辑/diff 不友好。
5. **对比 C**：事件溯源适合"状态完全由玩家行为动态产生"的游戏；本作历史是设计期常量，只需容纳玩家覆盖，C 是过度设计且更难保证确定性。

## 后果
- **正向**：数据局部、作者友好、求值确定、易序列化、天然可逆（撤销 = 弹 Override 再 resolve）。
- **负向**：跨实体的"某时刻全局约束"（压力板/闸门）不能在数据层表达，需在管线的**派生状态重算**阶段处理（见 ADR-002、§3.8）。
- **已消解风险**：原担心"道具携带穿越时刻需强因果检测"——GDD 明确**不做因果物理模拟**，携带穿越只是 forward Override，悖论免疫由 resolve 确定性保证。此风险已不存在。
